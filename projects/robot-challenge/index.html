How a detection becomes a collection action

Methodology

01 Dual-camera perception and a shared bearing frame

A YOLO segmentation node processes two angled cameras on the Jetson Orin Nano. Detections from both cameras are merged into one UDP message, so the navigation process receives a consistent pair of views.

Bearing conversion
Reproject each horizontal detection coordinate into a common forward-facing camera frame using camera intrinsics and the camera toe angle.
Camera monitoring
Check for frozen image streams and retain raw frames for debugging model behavior against robot motion.

Sources: Dual-camera inference · Detection-to-decision interface · On-device latency benchmark · Field tuning

02 Geometric filtering before a collection decision

Object labels alone do not determine a target. Navigation combines the class prediction with confidence, viewing direction, estimated range, and ownership of the current arena cell.

Range normalization
Scale segmentation-mask area with squared range before applying area gates, reducing the dependence on apparent object size.
Observation budget
Tune detection evidence together with scan speed: a fast pass may expose an object in only a few inference frames.

normalized mask area = mask area × (range / reference range)²

Sources: Dual-camera inference · Detection-to-decision interface

03 Collection planning under mechanical constraints

A fixed sweep route is combined with live target decisions. The passive basket holds three objects: forward motion captures a target, while reverse travel can release the load. Collection, turning, and delivery therefore have to be planned together.

Route structure
Traverse arena segments, interrupt the sweep when the basket fills, and execute the corresponding return and deposit behavior.
Mechanism-aware motion
Account for the basket during alignment, braking, and reverse movement rather than treating collection as a separate actuator command.

Sources: Robot and competition setup

04 Sensor-informed motion and motor integration

The Jetson sends body-velocity commands to an ESP32 over USB serial. The controller drives four geared motors through individual motor drivers, with explicit axis conventions and wheel calibration.

Pose and turns
Use LiDAR wall fitting for pose and IMU-integrated yaw to terminate calibrated turn pulses.
Translation and stopping
Use LiDAR feedback for lateral motion and calibrated reverse-braking pulses for stops. Choose cruise speed within the measured braking range.

Sources: Motor interface and calibration · Motion primitives and measured limits · Braking implementation

Implementation notes & source evidence

The engineering problem

The robot had 180 seconds to find, collect, and deliver two target classes announced at match time. A Jetson Orin Nano ran perception and navigation on a four-wheel mecanum chassis. The key mechanical constraint was a passive, three-object basket: driving forward captured an object, while reversing released it. That made motion planning, stopping, and perception part of the same collection problem.

Sources: Robot and competition setup

From software commands to wheel motion

The Jetson sent body-velocity commands over a 115200-baud USB serial link to an ESP32, which commanded four JGB37-520 geared DC motors through DRV8871 drivers. The host interface explicitly converted its forward/right/yaw convention to the chassis axes and reapplied per-wheel feed-forward and encoder-direction calibration after connecting. Motion commands carried a duration and auto-stopped at the controller. The hot path sent commands without waiting for an acknowledgement, avoiding serial round-trip delays in the control loop.

Sources: Motor interface and calibration

Control choices driven by the mechanism

The team used a fixed sweep route with live collection decisions. LiDAR wall fitting supplied pose; an IMU integrated yaw to terminate calibrated turn pulses. Lateral moves used LiDAR feedback by default because the documented timed-strafe calibration left 4–7 cm error. Stops used a calibrated reverse-braking pulse, with a useful speed range around 42–57 cm/s. Cruise was therefore set near 44 cm/s rather than pushed toward the motor limit. Route corrections also had to respect the basket’s tendency to release its load during backward travel.

Sources: Motion primitives and measured limits · Braking implementation

Perception within the integrated system

My contribution included perception and model training alongside planning, data collection, hardware, and integration. The dual-camera vision node combined both cameras into one UDP message and reprojected detections into a common forward-facing bearing. Navigation then applied confidence, range-normalized mask-area, bearing, and grid-cell ownership checks. This interface connected the team’s perception implementation with its motion and collection logic.

Sources: Dual-camera inference · Detection-to-decision interface

What the integration makes clear

A detector’s offline accuracy is only one part of a usable robot. At the documented scan speed, an object could appear in only two or three inference frames, so demanding many repeated detections could reject real targets. The repository includes an Orin benchmark for model latency and a frame-freeze check for each camera. The engineering lesson is to choose the model, observation gates, and vehicle speed together, and to debug raw camera frames alongside motion logs.

Sources: On-device latency benchmark · Field tuning

Competition validation

Team 7 finished second with 140/200 points across two final runs, collecting three shape targets and two fruit targets per run. The repository includes run videos and documents the calibration limits of the competition prototype.
